## 问题一：侧边栏导航图标看不见

### 现状
- 侧边栏在 `static/common.js` 的 `renderSidebar()` 函数中渲染
- 导航项使用 `iconify-icon` web component（从 `https://code.iconify.design/iconify-icon/2.1.0/iconify-icon.min.js` 加载）
- 所有 11 个 HTML 页面都在 `<head>` 中加载了 iconify CDN 脚本

### 已尝试但未解决
- 已将侧边栏 logo 的 `<iconify-icon>` 替换为内联 SVG（可见但不理想）
- 已尝试通过 curl 验证 CDN 可访问（HTTP 200）
- 已添加 Cache-Control: no-cache 到 HTML 响应头
- 已添加 favicon 缓存破坏参数 `?v=2`

### 可能根因（需要 Codex 排查）
1. **Iconify CDN 在中国被墙/限速** — 虽然 curl 能通但浏览器环境下可能被拦截
2. **Iconify web component 初始化时机问题** — 页面通过 `innerHTML` 渲染，web component 可能在 DOM 插入前就已注册，导致新插入的元素不被识别
3. **CSS 样式冲突** — `.nav-item` 的 `color` 变量可能在某些主题下与背景同色

### 建议方案
**方案 A（推荐）**：完全放弃 iconify CDN，所有图标换成内联 SVG  
- 优点：零依赖，100% 可靠  
- 缺点：需要为每个图标写 SVG path
- 已在 `common.js` 中定义了 `NAV_ICONS` 对象（10 个图标的 SVG path），导航项渲染也改为 SVG
- **但奇怪的是替换后仍然看不见** — 可能是 CSS 问题或浏览器缓存

**方案 B**：换用国内 CDN 镜像  
- `https://cdn.jsdelivr.net/npm/iconify-icon@2.1.0/dist/iconify-icon.min.js`
- `https://unpkg.com/iconify-icon@2.1.0/dist/iconify-icon.min.js`

### 相关文件
| 文件 | 说明 |
|------|------|
| `static/common.js` | `renderSidebar()` 函数，`NAV_ITEMS` 和 `NAV_ICONS` 定义 |
| `static/design-system.css` | 侧边栏样式（`.sidebar`, `.nav-item`, `.sidebar-logo` 等） |
| 所有 `static/*.html` | 页面入口，均加载了 iconify CDN |

## 问题二：RPA 扫码登录后账号未保存 / 流程卡住

### 现状
- 后端 API 接口已完整实现并通过单元测试：
  - `POST /api/accounts` — 创建账号
  - `POST /api/accounts/{id}/scan-login` — 启动扫码登录（后台任务打开浏览器、轮询登录态、保存 cookie）
  - `GET /api/accounts` — 返回账号列表（含 `ready`、`missing`、`credential_kind` 字段）
  - `PUT /api/accounts/{id}/credentials` — 写入凭据（API 平台用）
- `scan-login` 后台任务调用 `publish_readiness.py` 的 `readiness()` 判断就绪度

### 已尝试但未解决
- 前端 `accounts.html` 已实现了绑定弹窗（多步向导）：选平台 → 填名称 → 调用 `POST /api/accounts` 创建 → 调用 `POST /api/accounts/{id}/scan-login` 启动扫码 → 轮询 `GET /api/accounts` 等 `ready` 变 true → 跳转完成页
- **扫码后一直卡在 "正在打开登录页"**，轮询从未检测到 `ready: true`

### 可能根因（需要 Codex 排查）
1. **`scan-login` 后台任务执行失败** — 看 `app.py` 中 `_run_scan_login()` 函数：
   - 它启动有头浏览器（`headless=False`）
   - 导航到 `adapter.login_url`（小红书：`https://creator.xiaohongshu.com/login`，抖音：`https://creator.douyin.com/`）
   - 轮询 `_logged_in_selector()` 最多 180 秒
   - 检测到登录后调用 `db.update_account_credentials()` 保存 cookie 并 `db.update_account_status()` 置 active
   - **如果浏览器启动失败（macOS 权限/Playwright 未安装）、选择器不匹配、或用户未在规定时间内扫码 → 都可能导致卡住**
2. **就绪度判定逻辑问题** — `publish_readiness.readiness()` 检查 `credentials` 中是否有 `cookies` 数组且非空。`scan-login` 使用 `build_credentials(cookies)` 写入。需确认格式一致
3. **前端轮询逻辑问题** — `pollAddReady()` 每 2 秒调用一次 `GET /api/accounts`，检查 `acc.ready`。如果账号的 `credential_kind` 不是 `cookie` 或 `ready` 字段被后端计算为 false → 轮询永不结束
4. **Chrome 的强缓存** — 虽然加了 Cache-Control 头但只对 HTML 有效，API 响应可能被缓存导致前端拿到旧数据

### 建议调试步骤
1. 看后端日志（`/tmp/logiflow.log`）：扫码启动后有没有打印 "扫码登录成功" 或异常堆栈
2. 在浏览器开发者工具 Network 标签观察 `GET /api/accounts` 的响应，看该账号的 `ready` 和 `credentials` 字段内容
3. 手动调用 `POST /api/accounts/{id}/scan-login`（用 curl）确认后端行为

| 文件 | 说明 |

| `app.py` | `_run_scan_login()` 函数（约 350 行）、`POST /api/accounts/{id}/scan-login` 端点 |
| `adapters/rpa_base.py` | `RpaAdapter` 基类（`_logged_in_selector()`, `check_login()`, `build_credentials()`） |
| `adapters/xiaohongshu.py` | 小红书适配器（`login_url`, `_logged_in_selector()`） |
