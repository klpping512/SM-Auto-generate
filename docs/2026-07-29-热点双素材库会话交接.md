# 热点双素材库与 AI 对话成片｜会话交接

> 更新时间：2026-07-29 13:12:26 CST  
> 面向对象：没有本次对话上下文的新会话、开发和测试人员  
> 当前结论：双素材库的“定时入库”和“从已确认 Hook 生成视频”主体已完成；**AI 对话的一键视频尚未完全接入双素材库成片链路**，因此整个任务未完成。

## 1. 任务目标

为 Buffalo 建立一个可持续更新的热点内容链路：

1. 系统从已授权信源采集南非热点候选。
2. 内置模型结合 Buffalo RAG，在下载前判断热点是否能自然引出电商履约、跨境、仓配或末端配送问题。
3. 对入选长视频下载、语音/视觉分析、裁剪吸睛的真实 Hook，并以标题、画面事实、物流切入点等结构化字段入“热点素材库”。
4. 用户只需用自然语言描述主题；有已确认 Hook 时，系统组合热点 Hook、Buffalo 原有素材、TTS、字幕和 CTA 生成 50–90 秒视频；无匹配时进入定向采集队列，不能硬凑无关热点。
5. 全链路由项目内模型调度，不依赖 Codex/GPT 做每条内容决策。

## 2. 当前已完成的能力

### 2.1 定时热点 Hook 入库

相关代码：`scheduler.py`、`hotspot_hook_intake.py`、`hotspot_intake_sop.py`、`app.py`。

- 服务启动时通过 `app.py` 的 lifespan 启动调度器。
- 热点候选抓取频率：每 6 小时。
- Hook 入库任务频率：每 3 天，任务名 `hotspot_hook_library_sync`。
- 默认要求候选为授权长视频；当前代码门槛为时长不少于 180 秒。
- 先读取候选元数据（默认最多 12 条），再由项目内模型 + Buffalo RAG 决定是否值得下载；下载前不应靠标题猜测内容。
- 当前单轮最多处理 4 条模型选中的母片。下载后调用共享物化流程：下载 → ASR/OCR/视觉分析 → 镜头分析 → 模型策展 → 事件 Hook 代理片生成。
- 可进入可用库的 Hook 必须具备：`what_happened`、`hook_reason`、`logistics_question`、`confirmed` 审核状态、可用本地代理片。待确认、没有“发生了什么”的旧片段不会被 AI 对话和成片检索。
- 清理任务每天 03:45 运行；超过 10 天的 Hook 才可回收，最近 3 天、被活动项目引用或忙碌中的媒体永远跳过。

### 2.2 双素材库正式成片

相关代码：`hotspot_video_planner.py`、`hotspot_preview_narration.py`、`video_composition_policy.py`、`video_generation.py`、`video_renderer.py`。

- 热点 Hook 的职责：说明真实发生了什么，只引用已确认片段和精确时间范围。
- Buffalo 原有素材的职责：展示镜头中可见的仓内、配送、车辆、员工等动作，不把热点说成 Buffalo 已解决的服务证明。
- Buffalo 自有图片可作 1–2 秒的过渡，最多 3 张、不可相邻、不可重复，不得冒充扫描、同步、出库或服务结果。
- 固定 Buffalo CTA 使用用户提供的品牌结尾图；它是收束，不是热点证据。
- 成片硬门禁：同一 `asset_segment_id` 只能一次；同一 Buffalo 原始视频默认一次；同一热点母片最多两个不重叠 Hook；图片不可重复；真实视频不得循环填满旁白；终片校验来源重复、范围重复、字幕时间线、转场后音画同步。
- 文案与事实审核当前采用项目内 Qwen 3.7 Plus 路由；Qwen TTS 用于旁白。MiniMax 曾尝试但不再承担 `planner_text` 与 `critic`，原因是严格 JSON、短镜头和事实边界稳定性不足。不要在文档、日志或代码中写入任何 API Key。

### 2.3 信息图已被硬禁用

本次刚完成的修复，相关文件：

- `video_composition_policy.py`
- `hotspot_video_planner.py`
- `hotspot_preview_narration.py`
- `video_generation.py`
- `video_renderer.py`
- `scripts/run_dual_library_preview.py`

规则如下：

- 禁止信息图、流程图、PPT 卡片、数据卡、地图卡、标题卡、幻灯片及其常见类型别名。
- 规划器不会生成这类镜头；旧脚本或模型输出包含这类镜头时，脚本归一化、热点证据门禁、素材匹配和最终渲染都会直接失败。
- 无真实素材时应提示补充未使用的热点 Hook、Buffalo 自有视频或 Buffalo 自有图片；不得循环旧叉车视频，更不得生成空白解释卡。

此前用户截图中的“路线影响说明 / 订单节点说明”是旧解释卡产物，已经不允许再出现。运行中的服务需要重启后才会加载此硬门禁。

## 3. 当前未完成项与卡点

### P0：AI 对话尚未直连双素材库视频生成

当前 `POST /api/ai/chat` 已做两件事：

1. 调用 `_retrieve_confirmed_chat_hooks()`，从已确认 Hook 库让内部模型检索热点；匹配不到时写入 `hotspot_discovery_requests` 定向采集队列。
2. 调用 `ai_engine.chat_platforms()` 生成各平台文案。

但聊天页的“生成视频”仍将通用文案输出创建为 `source_type=chat` 的通用视频项目；它没有把 `hotspot_retrieval.hooks` 锁定后交给 `generate_topic_brief_video()` / 双素材库规划器。因此不能宣称“用户只聊天就已经能稳定产出热点 + Buffalo 双素材库视频”。

应完成：

- 聊天返回 `matched` Hook 时，为“生成视频”创建 `topic_brief_dual_library` 项目，使用命中的 `event_clip_id`，再调用双素材库规划、内置模型旁白、TTS、渲染和终片质量门禁。
- 聊天返回 `queued` 时禁用视频生成，清晰显示“暂无可用热点，已进入定向采集队列”，但仍可生成普通图文内容。
- 不要在聊天请求中直接下载母片或等待下载完成；这样会拖慢对话，也会绕过三天任务的模型筛选和事实核验。

### P1：定时任务“已配置”不等于“已跑完本周期”

- 代码已注册 3 天任务，且服务启动默认开启预热开关；但新会话不能凭代码断言某一轮已经实际下载、分析并入库。
- 需要查询 `hotspot_media` 状态、审计日志 `prewarm_authorized_hotspot_media` 和 Hook 库条目，或手动运行授权预热脚本，才能报告本轮实际产物。
- APScheduler 的 interval 任务通常在服务启动后的下一个周期执行；若需要立即补库，应由管理员明确触发一次受控预热，不要假装定时任务已即时跑完。

### P1：当前预热规模与“全量下载”预期不一致

- 当前实现：最多读取 12 条元数据、最多下载 4 条模型选中的母片。
- 用户曾提出“周期内尽量全面分析素材”的方向。若目标改为全量，需要先确定存储、带宽、分析时长和并发上限，再调整批量策略；不能直接取消上限导致定时任务失控。

### P1：授权字段仍使用历史 `rights_tier=green` 过滤

- 用户已说明授权信源已获许可，并提出取消红绿灯分级。
- 但 `scheduler.py` 当前仍筛选 `rights_tier="green"`。下一轮应将其改为清晰的“已授权/可处理”状态或审批记录，不再向用户暴露红绿灯措辞；修改前要核对数据库迁移和已有候选数据。

### P2：成片质量仍需真实验收

- 已生成过 56.6 秒的无重复来源技术验收片，技术检查通过；但信息图硬禁用是在之后完成的。
- 下一条正式验收片应从当前已确认 Hook + Buffalo 素材重新生成，人工检查：开头 Hook 是否真实有吸引力、画面不重复、图片过渡自然、字幕位置与遮罩大小、TTS/字幕/画面同步、CTA 是否自然。
- 不要只看 pytest 通过就声称视觉质量完成。

## 5. 易踩坑与禁止事项

- 不要把“候选热点”“已下载母片”“已确认 Hook”“可进成片”混为同一个状态。
- 不要把热点母片放进 Buffalo 原有素材库。母片属于热点来源层；真正用于成片的是其已确认 Hook。
- 不要由 Codex/GPT 人工替系统挑选 Hook；选题、Hook、叙事和事实审核应由项目内模型 + RAG 决策，并保存模型决策记录。
- 不要凭标题、新闻滚动条或模糊画面推断物流事实；无 `what_happened` 的素材不得入可用 Hook 库。
- 不要把市政垃圾、治安、政治、娱乐等边缘事件硬接到 Buffalo；无合规物流切入时应该拒绝。
- 不要为凑时长循环真实视频，也不要生成信息图/PPT。素材不足应失败或进入采集队列。
- 不要把静态图片当作“系统已扫描/同步/配送成功”的证据；它只能承担短过渡。
- 不要把服务启动、定时任务注册、测试通过误报成“真实下载/成片已完成”；必须用任务记录、入库条目和最终视频质检证明。
- 不要在交接文档、Git、日志、截图或测试输出中留下 API Key、Token、Cookie、密码或代理凭据；此前用户提供的临时密钥应由持有人自行轮换。
- 工作区本来就存在大量用户未提交改动；不要 `git reset`、不要清理无关文件、不要未经授权提交或推送。
