# 公众号图文长文发布 — 阶段 0 可执行指令（v1）

> 总指挥出品 · 2026-08-06　执行工具：**opencode**（非 Cursor）
> 依据：同目录 [`公众号图文发布-方案设计.md`](公众号图文发布-方案设计.md)（v3，§5.1–5.6 全部拍板）。
> 一句话背景：给"图文长文"建一个**独立于短视频链路**的最小内容生产闭环——人工投喂资料包 → 结构化生成（事实锚定到资料包） → 人工选图 → 产出可直接复制粘贴/二次排版的素材包 → 人工登录公众号后台手动发。**本轮不接 API、不建独立信源采集、不建 RAG 证据库、不做终审 UI。**

---

## 0. 范围边界（防写多 / 防写少）

**属于阶段 0（本指令要做的）：**

- 新表 `articles`（3 态状态机：`draft` / `ready` / `published`）
- 选题投喂 CLI：人工把资料包存成一个 JSON 文件喂给系统，建草稿
- 生成模块：调用现有 `model_router`（复用 `planner_text` 路由），产出结构化正文 JSON，硬约束"数字类断言必须能追溯到资料包"
- 配图选择 CLI：复用现有 `database.list_assets` + `asset_taxonomy`，人工从候选里选，不做自动配图
- 渲染 CLI：把结构化 JSON 渲成 `article.md` + `meta.json` + 图片文件，落到 `data/articles/{slug}/`
- 发布标记 CLI：`ready → published` 的一行状态流转（人工手动发完之后跑）

**明确不做（防止 opencode 顺手扩大范围）：**

- 不接微信官方 API（草稿箱/素材上传/群发）——账号未认证，且这是阶段 1 的事
- 不建独立信源采集轨道（RSS/爬虫/RAG）——资料包由人工投喂
- 不做 Web 终审 UI——校对在生成的 Markdown 文件里做，人工直接改文件
- 不做自动配图（模型选完图直接落地）——候选必须人工确认后再落地，因为选错图无法在发布前被机器发现
- 不动 `adapters/huimei.py` 或任何发布队列——阶段 0 产出的是文件，不进 `queue` 表

## 2. 对抗审查（自查，opencode 落地前应确认已规避）

| # | 风险 | 后果 | 规避方法 |
|---|------|------|----------|
| R1 | 资料包 JSON 没有 schema 校验，人工手抖传个空数组/漏字段 | 生成 prompt 拿不到证据素材，模型要么拒答要么editorializes | intake 脚本对资料包做最小结构校验（至少 1 条 `materials`，每条至少有 `excerpt` 和 `source_note`），不合格直接拒绝建草稿并打印哪里错了 |
| R2 | 配图选择环节"自动挑最匹配的直接落地" | 选错图在发布前不会被人发现（南非本地新闻配图放到跟老挝配图的坑一样，是南非项目自己踩过的教训类风险） | 配图 CLI 只出候选列表（含 asset_id、source、缩略图路径），人工敲编号确认后脚本才真正复制文件；不给"全自动"参数 |
| R3 | 模型嘴上说遵守事实锚定，实际还是编了具体数字 | 文章里出现无来源的假数字，比没图更致命（这是长文体裁特有的风险，短视频口播没有这个问题） | 生成结果落地前，渲染脚本用正则扫一遍正文，抓出"数字+单位/货币/日期格式"的片段，逐条核对是否命中 `evidence_footnotes` 里登记的资料包引用；未命中的一律替换成 `[待核实：原文写的是"…"，请人工核实来源]` 并在 CLI 输出里汇总提醒，不静默通过 |
| R4 | slug 冲突把已渲染的素材包目录覆盖掉 | 已经人工改过的 `article.md` 被无声覆盖 | `articles.slug` 建 `UNIQUE` 约束；渲染脚本落盘前检查 `data/articles/{slug}/` 是否已存在且非空，存在则要求 `--force` 显式确认才覆盖 |
| R5 | 复用 `planner_text` 路由会不会跟热点策展的 job 撞车 / 抢 budget | budget 是按 `job_id` 隔离的（`model_router.create_budget` 是 sticky per-job），`route_scoped_job_id` 已经把 role 编进 job_id 命名空间，不会撞车；但仍要用独立前缀（如 `article-gen:{article_id}`）保证一眼能在诊断表里区分是文章生成还是热点策展 | 生成模块的 `job_id` 统一用 `f"article-gen:{article_id}:{attempt}"` 或等价前缀 |
| R6 | `model_router.call_text` 是 `async def`，CLI 脚本是同步跑的 | 直接调用会报 coroutine 未 await | 沿用 `hotspot_hook_curator.py` 里 `asyncio.run(model_router.call_text(...))` 的既有写法，不要另造一套 |
| R7 | 图片选源规则（za-stock vs media_assets）如果写死成"某个函数返回 True/False 才能用" | 现有 `_is_buffalo_usable_source` / `apply_overclaim_guard` 是短视频口播文案链路的组件，字段含义不保证直接适用图文；硬套过去容易在没查清楚的情况下引入错误依赖 | 阶段 0 **不复用**短视频链路的图源判定函数；配图 CLI 自己按 `assets.source` 字段简单分组展示（`za_stock_license` 一组、其它一组），标签直接告诉人工"这组是免版权通用素材，不能用来证明 Buffalo 自己的能力；这组是自家实拍"，判断交给人工，不写自动化门禁逻辑 |

## 3. 可粘贴指令（给 opencode）

### Step 1 — 数据模型：新建 `articles` 表

```
在 database.py 的 init_db() 里那段 conn.executescript("""...""") 的现有 CREATE TABLE 语句之后，
新增一张表（照抄 hotspot_sources 表附近的写法：AUTOINCREMENT 主键、datetime('now') 默认时间戳、
FOREIGN KEY 关到 users(id)）：

CREATE TABLE IF NOT EXISTS articles (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    slug TEXT NOT NULL UNIQUE,
    title TEXT NOT NULL,
    topic_brief TEXT NOT NULL DEFAULT '',
    materials_json TEXT NOT NULL DEFAULT '[]',
    reference_style TEXT NOT NULL DEFAULT '',
    generated_content_json TEXT NOT NULL DEFAULT '{}',
    evidence_footnotes_json TEXT NOT NULL DEFAULT '[]',
    unresolved_claims_json TEXT NOT NULL DEFAULT '[]',
    status TEXT NOT NULL DEFAULT 'draft',
    output_dir TEXT,
    created_by INTEGER,
    created_at TEXT DEFAULT (datetime('now')),
    updated_at TEXT DEFAULT (datetime('now')),
    FOREIGN KEY (created_by) REFERENCES users(id)
);

字段说明（写进同一段 SQL 上方的注释即可，不用另开文档）：
- slug：URL 安全的短标识，同时是 data/articles/{slug}/ 的目录名，人工在 intake 时手动指定或按标题自动 slugify
- materials_json：资料包原文，结构见 Step 2 的 schema
- generated_content_json：生成结果的结构化正文（intro/sections/conclusion），结构见 Step 3
- evidence_footnotes_json：断言→资料包来源的映射，结构见 Step 3
- unresolved_claims_json：Step 3/Step 5 扫描出的"未能追溯到来源、已被替换成 [待核实]"的清单，供人工核对
- status：draft（草稿，含"资料包已建/生成中/待选图"全部子阶段）→ ready（素材包已渲染完成，等人工发）→ published（人工手动发完后标记）

在 database.py 里加一个 record_schema_migration("2026-08-06-articles-table", "新增 articles 表：公众号图文长文生产") 调用（照抄现有同类迁移记录的调用位置和写法，不要漏——这是仓库里已有的迁移记录约定，见 record_schema_migration 函数）。

不需要写 _ensure_column 迁移分支：这是全新表，走 CREATE TABLE IF NOT EXISTS 首次建库/首次升级都能生效，不存在老库缺列的问题。
```

### Step 2 — 选题投喂 CLI：`scripts/create_article_draft.py`

```
新建 scripts/create_article_draft.py，脚本骨架照抄仓库里 scripts/ 目录现有 CLI 的标准写法
（argparse + 把项目根目录加进 sys.path + load_dotenv + db.init_db()，参考同目录任意一个现成脚本，
例如 scripts/reseed_hotspot_sources.py 的头部结构，风格保持一致）。

【输入】
--materials-file PATH：一个人工手工整理好的 JSON 文件，结构：
{
  "slug": "sa-poe-registration-guide",
  "title": "南非PoE登记指南：中国卖家绕不开的这道坎",
  "topic_brief": "一句话说明这篇要讲什么、目标读者是谁",
  "reference_style": "可选：参考同行范文的链接或一段说明，仅用于生成时对标结构，不作为事实来源",
  "materials": [
    {"excerpt": "资料原文片段，摘录要尽量保留可核实的具体数字/时间/机构名", "source_note": "来源说明，比如'南非税务局官网 2026-07 公告'", "source_url": "可选"}
  ]
}

【校验（对应 §2 R1，不合格直接拒绝，不建草稿）】
- slug：非空、只允许小写字母数字连字符，且在 articles 表里唯一（查重，冲突则报错退出，不做自动改名）
- title：非空
- materials：数组长度 >= 1，且每一条都必须同时有非空 excerpt 和非空 source_note（source_url 允许空）

【落库】
校验通过后 INSERT INTO articles(slug, title, topic_brief, materials_json, reference_style, status, created_by)
status 固定写 'draft'。打印新建的 article id 和 slug。

【输出】
--dry-run 参数：只跑校验、打印会插入的内容，不实际写库，方便人工先自查资料包格式对不对。
```

### Step 3 — 生成模块：`wechat_article_generator.py`

```
新建 wechat_article_generator.py（项目根目录，跟 hotspot_hook_curator.py 同级，风格参考它的组织方式：
一个 PROMPT_VERSION 常量 + 拼 prompt 的私有函数 + 对外的生成函数 + 复用它里面的 _extract_json）。

核心对外函数：
def generate_article(article_id: int) -> dict
  1. db.get_article(article_id)（同时要在 database.py 里补一个 get_article(article_id) -> dict|None 的读取函数，
     参照仓库里其它 get_xxx 单行读取函数的写法，SELECT * FROM articles WHERE id=?）
  2. 反序列化 materials_json，拼系统 prompt + 用户 prompt：
     - 系统 prompt 里写死硬约束（原文照抄，不要意译弱化）：
       "严格返回 JSON。正文中出现的任何具体数字、费用、期限、日期、机构名称，
        必须能在下面提供的资料片段中找到依据；找不到依据时改写成不含具体数值的模糊表述，
        并在 evidence_footnotes 里跳过该句，不允许编造或从常识补充数字。
        文章结构：导语（背景+读者痛点+结构预告）→ 分节正文（每节一个小标题，
        可选一个结构化对比字段，字段名和值都用文本描述，不要输出 HTML）→ 结尾总结。"
     - 用户 prompt 里把 topic_brief、reference_style（如有）、materials 逐条列出（带编号，
       编号用于后面 evidence_footnotes 回指）
  3. job_id = f"article-gen:{article_id}:{attempt}"（对应 §2 R5，attempt 从 1 开始，重试时递增，
     不要复用同一个 job_id 覆盖 budget）
  4. model_router.create_budget(job_id, max_calls=2, max_input_tokens=14_000,
     max_output_tokens=model_router.required_output_budget("planner_text", 1_500), reset=True)
     —— max_calls=2 含义同 hotspot_hook_curator：1 次生成 + 1 次 JSON 解析失败重试
  5. asyncio.run(model_router.call_text(job_id, "planner_text", messages,
     prompt_version=PROMPT_VERSION, max_output_tokens=1_500))
     —— 复用现成的 "planner_text" 路由，不新增路由配置（对应 §2 R6，照抄 hotspot_hook_curator.py 里
     asyncio.run(model_router.call_text(...)) 的调用方式，不要自己另起一套 event loop 处理）
  6. 用 hotspot_hook_curator._extract_json 解析返回内容（直接 import 复用，不要复制一份，
     它已经处理了代码围栏和 <think> 块）；解析失败时按 attempt+1 重试一次（use_cache=False），
     两次都失败则返回状态 "generation_failed" 并把原始 raw 内容打印出来，不写入 articles 表
  7. 期望的返回 JSON 结构：
     {
       "intro": "导语文本",
       "sections": [
         {"heading": "小节标题", "body": "正文段落", "comparison_card": {"字段名": "值", ...} 或省略},
         ...
       ],
       "conclusion": "结尾总结",
       "evidence_footnotes": [
         {"claim_text": "文中某句包含具体数字的原句", "material_index": 1}
       ]
     }
     material_index 对应用户 prompt 里给资料片段标的编号
  8. 生成成功后：UPDATE articles SET generated_content_json=?, evidence_footnotes_json=?,
     updated_at=datetime('now') WHERE id=?（status 仍保持 'draft'，不在这一步流转状态——
     选图和渲染都还没做）
  9. 返回结构化结果字典，供 CLI 脚本打印摘要（分几节、字数、evidence_footnotes 条数）

再建一个薄 CLI 包装：scripts/generate_article.py --id N，就是调用上面这个函数并打印结果，
方便人工单独重跑生成（比如觉得写得不好，想重新生成一次）。
```

### Step 5 — 渲染 CLI：`scripts/render_article_package.py`

```
新建 scripts/render_article_package.py，标准 CLI 骨架同 Step 2。

【前置检查】--id N 对应的 article：generated_content_json 非空（Step 3 已跑）、
image_selections_json 非空（Step 4 已跑，至少封面选过），否则报错退出并提示先跑哪一步。

【事实核查扫描（对应 §2 R3，硬约束的最后一道闸）】
写一个正则，扫 intro/每个 section.body/conclusion 里形如
"数字+单位"（%、元、天、年、周、月、R、ZAR、$ 等常见计量/货币/时间单位紧跟数字，
或者形如 YYYY 年/YYYY-MM-DD 的日期格式）的片段。
对每个命中片段，检查它是否被包含在 evidence_footnotes_json 任意一条 claim_text 里
（简单子串包含判断即可，不用做语义匹配）。
命中但未被登记进 evidence_footnotes 的，追加进 articles.unresolved_claims_json，
并在渲染出的 Markdown 正文里，把该片段原样保留但前后加上 `【待核实：』…『】` 标记
（不要替换掉原文，让人工自己判断改成什么，只是打个醒目标记，防止人工review时漏看）。

【渲染 Markdown】
按以下结构拼 data/articles/{slug}/article.md：
  # {title}
  {intro}

  ## {sections[0].heading}
  {sections[0].body}
  （如果有 comparison_card，渲成一个 markdown 表格，两列：字段 / 值）
  ![](images/section-01.jpg)  ← 仅当该节 Step 4 选了图才插入这一行

  ## {sections[1].heading}
  ...

  ## 最后的话
  {conclusion}

  ---
  **资料来源**
  1. {evidence_footnotes[0] 对应的 material 的 source_note}（{source_url 如有})
  ...

【写 meta.json】
{
  "article_id": ..., "slug": ..., "title": ...,
  "materials_sources": [资料包里每条的 source_note 列表],
  "unresolved_claims": [同 unresolved_claims_json],
  "rendered_at": "当前时间"
}

【落盘保护（对应 §2 R4）】
渲染前检查 data/articles/{slug}/ 是否已存在且目录非空；存在则要求显式传 --force 才允许覆盖，
否则报错退出并提示"已存在，加 --force 覆盖"。

【收尾】
写完文件后：UPDATE articles SET output_dir=?, status='ready', updated_at=datetime('now') WHERE id=?
终端打印：产出目录路径、unresolved_claims 条数（>0 时用醒目文字提醒"有 N 处待核实，
发布前必须人工确认"）、正文字数、下一步提示"人工检查 article.md，确认无误后手动排版发布，
发完后跑 scripts/mark_article_published.py --id N"。
```

### Step 6 — 发布标记 CLI：`scripts/mark_article_published.py`

