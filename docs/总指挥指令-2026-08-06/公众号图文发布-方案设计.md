# 公众号图文发布 — 方案设计（总指挥出品 · v2 已过对抗审查，剩 2 项待拍板）

> 2026-08-06。用户提供南非物流同行「炫思速运」两篇公众号范文作参考，要求设计公众号发布方案。
> 口径已定：内容形态 = **独立选题的图文长文**（不复用短视频素材）；账号 = **未申请 API 权限，本轮只设计到"人工终审后待发"，不做自动发布**。
> **v2 修订说明**：v1 经对抗式审查，`evidence_harness.py` 只有 111 行、输入是**现有 hotspot 条目**（`db.get_hotspot`）、无独立文档抓取能力——我已复核确认，审查成立。核心问题：v1 通篇在解决"怎么自动化生产"，没先回答"产能 1–2 篇/周时，自动化值得吗"（呼应 08-04 指令"把力气使错层"的教训）。v2 采纳审查建议，阶段 0 砍掉独立信源采集 + RAG 证据库 + 5 态状态机，改为人工投喂资料包 + 3 态。
> 本文是方案设计，**末尾决策点拍板后，才产出下一轮可直接粘贴的执行指令**（本项目由 **opencode** 执行，非 Cursor，指令格式同样适用）。

## 0. 一句话背景

distribution-manager 今天的发布链路是「南非本地热点新闻切片 + Buffalo 自有素材 → FFmpeg 拼片 → 短视频」，覆盖抖音/小红书/X/Facebook（真实可用）+ 9 个走 `HuimeiAdapter` 占位的次要平台（含 `wechat_mp`，因 huimei CLI 未装等于没做）。公众号图文长文是**结构完全不同的新内容单元**——不是给 `wechat_mp` 接个真适配器就完事，选题域、生产流程、排版形态都要新建一条产线。

## 1. 现状盘点（代码探查结论）

| 层 | 现状 | 与图文需求的落差 |
|---|---|---|
| 适配器 | `adapters/huimei.py`（21 行纯壳），`CREDENTIAL_KIND="none"`，靠外部 `huimei` CLI（**未安装**），实际发布必炸 | 微信公众号真实发布需要 AppID+AppSecret（或扫码登录）+ 素材上传两步走（图片先传拿 `media_id` 才能引用），今天**零凭证建模** |
| 适配器契约 | `publish(title, content, tags, images, video, account)`，`content` 是一段拼接字符串，各平台适配器各自截断拼接 | 公众号图文要的是「标题 + 封面 `thumb_media_id` + 摘要 `digest` + 受限富文本 HTML 正文」，形状对不上 |
| 数据模型 | 无通用「文章/Post」模型；`queue` 表最接近（`title/body/platform/hashtags/attachments/status`），但 `body` 是 flat 字符串 | 长文需要分节结构（标题/导语/N 个小节/结尾）+ 多图 + 封面图，`queue.body` 撑不住 |
| 选题信源 | 现有热点漏斗（RSS+YouTube）服务短视频 hook，关键词表 `hotspot_lexicon` 聚焦"仓储/清关/配送/运输"等**物流实体运作**话题，信源是南非本地新闻媒体 | 范文选题是"认证新规解读""电商平台招商动态"——是**面向中国卖家的南非市场情报**，跟"南非本地民生新闻"几乎不是一个信源域 |
| 证据设施 | `evidence_harness.py`（111 行）：`build_package(hotspot_id, ...)` 只读**已入库的 hotspot 记录**（`db.get_hotspot`），从标题/摘要切句子配 `source_url/publisher`，**没有独立抓取英文 PDF 公告 / 登录卖家中心页面的能力** | 若要支撑"信源→RAG证据"这套骨架服务图文选题，等于要新建一整套文档抓取设施，是净新增工程量，不是复用 |

## 2. 参考范文拆解（两篇同行文章，结构高度模板化）

| 版块 | 规律 |
|---|---|
| 标题 | `[具体事件/政策/主体]：[XX指南/入局指南]` —— 新闻由头 + 干货体裁副标题（如"南非PVoC与NRCS认证边界厘清：25类新规商品合规分类与成本测算指南"） |
| 头图 | **固定复用**的品牌 banner（LOGO + 目的地风光 + 二维码），跟正文内容无关，一次性做好长期不换 |
| 导语 | 无小标题的开篇段：背景是什么 → 读者（卖家）为什么关心/痛点在哪 → 本文将从哪几个维度回答（预告结构） |
| 配图 | 一张真实感强的场景图（海关查验现场 / 平台概念图），起视觉锚点作用，不承担论证功能 |
| 正文分节 | `01/02/03`艺术数字 或 `一/二/三`中文数字，加粗蓝色小标题；**遇到需要比较的信息，用统一字段模板并列**（如"办理周期/费用构成/有效期/适配场景"分别列举两种认证）——这是最值得复用的写作模式：结构化字段对比，不是自由散文 |
| 结尾 | "最后的话"总结段：呼应开篇 + 给行动建议/前瞻判断 |
| 文末物料 | **固定三件套**（一次性设计、逐篇复用）：①业务信息图（产品线列举）②品牌大字 slogan + "关于我们"③"产品介绍"四宫格图标 |

**结论**：这是典型 B2B 内容获客模型——用政策/平台动态当新闻钩子，正文给结构化的决策支持型干货，结尾软性导流到自家服务。Buffalo 可以直接对标这套模板，把"炫思速运"换成 Buffalo 的物流服务定位。

**v2 补充（对抗审查 A6）**：这套标题公式（"XX指南"）是**搜索型 B2B 获客打法**（读者带着问题去搜/被同行群转发），公众号本质是**推荐型/订阅型分发**（打开率靠订阅关系+标题痛点钩子+头图），照抄公式不等于照抄有效性。写作 SOP 应加硬规则：标题 ≤64 字（超出会被微信截断）；标题要点出具体读者利益/痛点，不是套用"XX指南"就算数。

## 3. 设计目标 / 非目标（本轮）

**目标**：打通「人工选题投喂 → 结构化生成（含事实锚定）→ 排版素材包」链路，产出**待发草稿**（结构化正文 + 封面图 + 配图包），供人工登录公众号后台手动发布。

**明确不做（本轮）**：
- 微信 API 对接（草稿箱 / 群发 / 素材上传接口）——账号未申请，留作阶段 1
- 复用短视频素材/热点做图文选题——用户已拍板独立选题
- 一步到位还原微信公众号编辑器所见即所得排版——见 §5.3
- **独立信源自动采集 + RAG 证据库**——v2 新增非目标，见 §4 模块 1 与 §5.2

## 4. 架构设计（v2：4 个模块，砍掉独立证据设施）

### 模块 1：选题 —— 人工投喂资料包（v2 改法，见 §5.2）

不建独立信源采集轨道。选题由人工完成（本来就在看雨果网/官网公告/同行文章），生成环节要的输入是一份**资料包**：

```
资料包 = {
  选题标题草案,
  投喂资料[]：{ 原文片段/链接, 来源说明 },   ← 这就是"证据"，人工挑好的，不用现爬
  可选：参考范文（结构对标用）
}
```

事实锚定（模块 3）直接从这份资料包里找依据，不依赖 `evidence_harness.py` 那套 hotspot 证据链路。**产能 1–2 篇/周时，每篇投喂 15–30 分钟完全可接受，且比爬官网 PDF 更可靠**（人工已经做了信息筛选和可信度判断）。

**复访触发**（不是永久关闭自动化）：如果实际产出节奏明显超过每周 2 篇、或人工投喂本身成为瓶颈，再回来考虑给这条线单独开信源采集轨道（不占现有 `MAX_ENABLED_SOURCES=12` 坑位，理由不变：话题域跟短视频热点不是一回事）。

### 模块 2：文章内容单元（数据模型，v2 状态机砍到 3 态）

```
标题（≤64字）
导语（背景/痛点/结构预告）
封面图引用
正文分节[]：{
  编号/小标题
  正文段落（含加粗关键词）
  可选：结构化对比卡片（字段模板，如 认证类型 → {办理周期, 费用构成, 有效期, 适配场景}）
  可选：配图引用
}
结尾总结
证据引用[]：{断言文本 → 资料包来源}
状态：草稿 / 待发 / 已发布        ← v2：5 态砍到 3 态（人工在环不需要"选题中/写作中"这类无人值守流水线状态）
```

### 模块 3：生成链路（写作 + 事实锚定，白名单来源改为资料包）

**核心风险不变**：具体数字类断言（周期/费率/金额/用户量）一旦编造，读者会当决策依据去用，代价比短视频文案高（呼应 pipeline-tuning 清关放闸/文案门禁教训）。

**v2 设计**：任何具体数字类断言，生成时必须能在**投喂资料包**里找到对应依据，标注来源（资料包条目 or 范文原文）；找不到依据的只能写模糊表述或标 `[待核实]`。证据标注直接以脚注形式呈现在产出的 Markdown 里，**不需要专门的终审 UI**——人工审稿时天然能看到"这句话依据哪条资料"。

### 模块 4：排版与固定物料

- 分节写作模板 + 结构化对比卡片 → 复用范文规律
- **配图来源两条腿**：①「南非免版权素材下载管线」（Pexels/Pixabay 归档素材）适合"新闻现场感"类通用场景图（海关查验、港口、仓库外观等无需 Buffalo 品牌露出的配图）；②现有 `media_assets` 素材库（Buffalo 自有实拍照片，8 类 `primary_category`）适合体现"Buffalo 真实能力"的配图（自家仓库/车队/员工作业实景）——两者按同一套 `asset_taxonomy` 分类语义调用。选哪条腿跟着该节内容是"客观陈述行业事实"还是"带出 Buffalo 自身服务"来定，沿用 pipeline-tuning 里"za-stock 来源不构成 Buffalo 能力证明"的口径
- **固定物料库**（头图 banner + 文末转化三件套）：一次性设计，逐篇复用，可复用 `media_assets` 里 brand 类素材做视觉底图
- **v2 新增：per-article 素材包目录约定**（对抗审查 A4），避免产出物到了人工排版环节图源还是乱的：
  ```
  /articles/{slug}/
    article.md          — 正文（含证据脚注）
    cover.jpg            — 封面图，建议 900×383
    images/
      section-01.jpg      — 正文配图，建议宽 900px
      section-02.jpg
    meta.json             — 标题/导语/来源资料包清单
  ```

## 5. 决策点（v2：已拍板 4 项，剩 2 项待你定）

### 5.1 内容单元存储 ✅ 已拍板：新建 `articles` 表，3 态状态机

`queue` 语义是"即将发送的一条消息"，跟文章创作的多阶段不是一回事，新建表成立；状态机从 5 态砍到 3 态（草稿/待发/已发布）——人工在环不需要给无人值守流水线设计的中间态。

### 5.2 选题信源 ✅ 已拍板（v2 改判）：不开独立采集轨道，人工投喂资料包

原方案（独立信源采集 + RAG 证据库）在产能 1–2 篇/周时 ROI 为负，且 `evidence_harness.py` 现状证实这是净新增工程（不是复用）。改为人工投喂，见模块 1。若产能明显提升再复访。

### 5.3 排版产出形态 ✅ 已拍板：Markdown + per-article 素材包（图片尺寸注记见模块 4）

微信公众号富文本只认内联 `style`、图片必须先传素材库换 CDN 链接，直接生成受限 HTML 工程量大且本轮不接 API，没必要现在啃。人工用秀米/135编辑器/Doocs-md 二次排版发布，产出物按素材包约定收敛，避免图源混乱。

### 5.4 事实锚定机制 ✅ 已拍板：硬约束，来源换成投喂资料包

"无来源不许写精确数字"这条硬约束保留，但依据来源从"爬官网证据"改为"人工投喂资料包 + 参考范文"——方向不变，实现前提换了之后更可落地。

### 5.5 固定物料视觉稿 ✅ 已拍板：我先起草文案 + 拼占位图

用 `media_assets`/免版权素材拼一版占位视觉，不阻塞产线；后续如需要真设计稿再替换。

### 5.6 公众号账号本身的状态 ✅ 已拍板（v3 澄清）：账号是分散的，各商务团队各自经营

不是"Buffalo 统一一个公众号"，而是**各商务团队各自注册/运营自己的账号**（与其它平台账号的运营方式一致——`accounts` 表本来就是"platform + 多行账号"的通用设计，不是单租户假设，这点不用改架构）。

**对阶段 0 的影响**：**不影响**。阶段 0 产出的是**跟具体账号无关的通用草稿包**（Markdown+配图+meta.json），哪个商务团队用哪个账号发、什么时候发，是人工在下游决定的事，不需要在生成阶段绑定账号。

**对阶段 1（API 自动化）的影响**：需要支持**同一 wechat_mp 平台下多个账号各自的凭证**（AppID/AppSecret 各团队各自的），这正好匹配现有 `accounts` 表"platform 下可以有多行账号"的既有设计，不需要新建多租户结构，只是要把 `CREDENTIAL_KIND` 从 `"none"` 换成真实的微信凭证 schema。阶段 1 立项时再定。

## 6. 分期路线图（v2：阶段 0 收窄 + 补验收指标）

| 阶段 | 范围 | 触发条件 |
|---|---|---|
| **阶段 0（本轮，收窄后的最小充分集）** | `articles` 表（3态）→ 人工投喂资料包入库（界面或直接 JSON/命令行）→ 结构化生成（事实锚定+资料包脚注）→ per-article 素材包产出 → 人工用现成工具排版发布 | 立即可做，不依赖账号权限；**不建**独立信源采集、RAG 证据库、终审专用 UI |
| **阶段 1** | 账号确认类型并认证 → 申请 API → 建凭证模型 → 素材上传接口 → 草稿箱接口 → 人工在草稿箱点发布 | 账号权限到手后 |
| **阶段 2（可选）** | 群发接口全自动发布 | 阶段 1 稳定运行、内容质量验证过一段时间后再评估，需按当时账号类型核实群发频次上限 |

**阶段 0 验收指标（v2 新增，对抗审查 A2 —— 08-04 指令的规格要求"验收只认数字"，本方案此前零指标）**：

| 指标 | 定义 | 用途 |
|---|---|---|
| 单篇产出耗时 | 从资料包投喂完成到素材包产出的耗时 | 判断生成链路是否真的省人力，还是比纯人工写还慢 |
| 待核实标记率 | 一篇文章里 `[待核实]` 数字断言数 / 总数字断言数 | 太高说明资料包投喂不够或事实锚定过严，需要调 |
| 人审改稿量 | 人工终审时实际改动的段落数 / 总段落数 | 判断生成质量是否可用，还是每次都要大改 |
| 选题到待发周期 | 从选题确定到素材包产出的自然日 | 判断这条产线能否撑起"1–2篇/周"的目标节奏 |
