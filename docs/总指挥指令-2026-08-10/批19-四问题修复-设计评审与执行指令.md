## 1. 问题1：素材复用（B+C）

### 1.1 根因（已核码）

1. **没有90%数字阈值**。`_marketing_hook_candidates`（app.py:1904）用的是布尔准入：
   - `strict_terms` 精确命中（事件类专有词，如 事故/边境/道路…）；
   - 再要求 `direct`（术语直接命中）**或** `profile_overlap`（语义画像重叠）**或** `intent_bridge`（意图桥）之一，否则 `relevance_low` 淘汰。
   - "降50%"在代码里没有对应物，不能直接改百分比。
2. **hotspot 侧没有使用冷却**。候选排序是 `(score, published_ts, hotspot_id)` 取 top（app.py:2112-2116）。`recent_session_hook_event_ids`（app.py:4624）只作用于**同一聊天 session**，跨 job 不共享；而 Buffalo 侧早已有 `usage_count`/`last_used_at` 冷却（`_owned_candidates` 排序、planner `_usage_freshness_penalty` :333）。热点 Hook 是漏网。
3. **库规模小放大了重复感**。当前 98 条可渲染 Hook（84 timely + 14 generic，分布 64 个母片）。高分事件分数稳定，每次都是同一批 top 赢 → 用户"测试几次素材都眼熟"。
4. 注意：渲染成功后 `video_renderer.py:1566` 已经 `db.bump_asset_usage(used_asset_ids, …)`，**热点素材的 asset_id 已被计次**（assets 表有 usage_count/last_used_at）。所以 B 不需要新表，只需在排序侧读取并施加惩罚。

### 1.2 设计

**B — 排序侧冷却惩罚**（治本，跨 job 生效）：
- 在 `_marketing_hook_candidates` 打分后、排序前，对每个 candidate 取 `hook_clips[0]["asset_id"]`，查 `assets.usage_count` / `assets.last_used_at`。
- 复用 planner 的 `_usage_freshness_penalty`（hotspot_video_planner.py:333）语义：距上次使用越近惩罚越大；0=从未/很久没用。
- 惩罚项加入 score：`score = 原score - min(usage, 5) - freshness_penalty`（与 `_owned_candidates` 的 rank 一致）。
- 素材库小时仍允许复用（只降权不排除），与现有 session 去重注释语义一致。

**C — 同分随机化轮换**（让画面不重复）：
- 每个 candidate 预计算一个 `tiebreak = random.random()`（只算一次，保证 sort key 稳定）。
- 排序 key 改为 `(score, published_ts, tiebreak)`。只在**分数完全相等**时由随机值打破；不同分仍按分严格排序。
- 为测试稳定：测试用新造素材（usage=0、无历史）分数不同，不受影响；涉及同分断言的测试，改为断言集合成员而非严格顺序，或用 monkeypatch 固定 random。

### 1.3 执行范围

- `app.py` `_marketing_hook_candidates`（~:2105-2116）：加 usage 查询 + 惩罚 + tiebreak 排序。
- 可复用 `hotspot_video_planner._usage_freshness_penalty`（跨模块 import，注意不要循环导入；如不便则复制等价实现并注释来源）。
- 不修改准入门禁（布尔准入保持现状，质量安全）。

### 1.4 测试

- `tests/test_hotspot_hook_library_gates.py:391`（无 renderable → `== []`）应继续通过（usage 查询对缺失 asset 返回 0 惩罚）。
- `tests/test_hotspot_hook_library_gates.py:416`（事故 > 边境，断言 `candidates[0]`）应继续通过（新造素材 usage=0，分数不同，无 tie）。
- 新增：
  - 同一 asset 连续两次渲染后，第二次候选排序中该 Hook 降权（低于同分未用 Hook）；
  - 同分两个候选连续调用两次，返回的 top 有轮换（集合断言）。

## 2. 问题2：字幕音画不同步

### 2.1 根因（已核码）

- `build_subtitle_cues`（video_renderer.py:889）按**每句字符数占全文比例**把句子时间摊到整段旁白时长上。
- 真实 TTS 的停顿/语速**不是字符比例**（短句拖长、数字单位读得慢、句间有静音）→ cue 边界与真实语音点错位。间歇性出现。
- 结构性对齐没问题：每镜视频/音频/字幕都 `-t duration` 对齐；crossfade 用 xfade+acrossfade 同一 `transition_duration`。错位只在 cue 颗粒度。
- mimo-v2.5-tts 返回只有 `message.audio.data`（base64 wav），无词级/句级时间戳（video_renderer.py:423-460）→ 无法用官方对齐信息。

### 2.2 设计（静音检测对齐）

- 新增 `_detect_speech_segments(wav_path, ffmpeg) -> list[(start, end)]`：
  `ffmpeg -i <wav> -af silencedetect=noise=-35dB:d=0.25 -f null -`，解析 stderr 里的 `silence_start`/`silence_end`，取补集得到语音段。返回空 → 无停顿（单段覆盖全长）。
- `build_subtitle_cues(text, duration, *, wav_path=None, ffmpeg=None)`：
  - 有 `wav_path`+`ffmpeg` 时：把 N 句按序映射到语音段（每句落到对应语音段区间内，句内仍按字符比例，但**边界对齐真实停顿**）；
  - 无参数时保持旧行为（`video_renderer.py:1551` 仅计数、无 wav 的调用不受影响）。
  - silencedetect 失败/无输出 → fallback 旧字符比例逻辑。
- 实际渲染调用点 `video_renderer.py:1379` 传入 `wav_path` 与 ffmpeg 路径（该函数作用域内已有 `ffmpeg, ffprobe = shutil.which(...)`）。

### 2.3 执行范围

- `video_renderer.py`：新增 `_detect_speech_segments`；改造 `build_subtitle_cues`（保持返回 dict 结构不变，`_write_ass` / `subtitle_sync_report` 无需改）。
- 不动 `_scene_command` / `_transition_concat_command`。

### 2.4 测试

- 新增：构造带明显静音间隔的 wav（可用 ffmpeg 生成正弦波+静音拼接），断言：
  - cue 边界不落在静音段内；
  - cue 数 == 句数；
  - `subtitle_sync_report` 无 gap、passed。
- 回归：`build_subtitle_cues(text, duration)`（无 wav 参数）行为与旧版一致。

## 3. 问题3：前端推发布队列

### 3.1 现状（已核码）

- 自动发布链路**已完整存在**：`scheduler.check_scheduled_publish`（scheduler.py:521，每分钟）扫 `status='queued' AND scheduled_at<=now` → `publisher.dispatch` → 适配器。无需新做。
- 缺口：成片验收页（static/video-project.html:598）成功态主按钮是"已完成"（disabled），**没有任何入队入口**；`POST /api/queue`（app.py:517）只收文本+附件，且 douyin 强制要求 video 附件。

### 3.2 设计

**后端 `POST /api/video-projects/{project_id}/enqueue`**（放 `routes/video_generation_routes.py`，跟随现有路由模式）：
- Body：`platforms: list[str]`、`account_targets: dict[str, int|None]`、`scheduled_at: datetime|None`、`title: str|None`（缺省取项目标题）。

- `db.add_to_queue(title=…, body="", platform=…, scheduled_at=(scheduled_at or now), status="queued", attachments=[video_att], target_account_id=…)`。
- 返回 queue item id 列表。
- 权限：`Depends(get_current_user)`；仅项目 owner / admin。

**前端（static/video-project.html）**：

- 说明文案：入队后由自动发布在 scheduled_at 到达时发布；内部预览文件不可入队（沿用现有 `!publishAllowed` 提示）。

### 3.3 执行范围

## 4. 问题4：热点素材过期清理

### 4.1 根因（已核码 + 日志实证）

1. **任务不是死代码，已注册但连续 missed**：scheduler.py:719 已注册每天 3:45 cron `hotspot_hook_library_cleanup`。日志证据：
   - 08-07 03:45 miss 0:00:51
   - 08-08 03:47 miss 0:02:43
   - 08-09 03:54 miss 0:09:37
   - 08-10 04:01 miss 0:16:04
   - 根因：apscheduler **默认 `misfire_grace_time=1秒`**——事件循环在 03:45 被占用 >1s，该次运行即被判"错过"跳过。错过时长逐日递增，说明 3:30 的 `cleanup_media_retention` 等任务在凌晨阻塞事件循环，且素材越积越多形成恶性循环。
2. **早期候选=0 是正确行为**：07-31/08-04/08-06 任务确实跑过，但当时素材未满 10 天。今天已有 **85 条**（`asset_id`+`downloaded`+`ready`）超过 10 天，任务一旦能跑就会清掉。
3. **年龄基准隐患**：`list_hotspot_hook_cleanup_candidates`（database.py:3376）用 `datetime(COALESCE(confirmed_at, created_at))`。已核实 35 条素材 confirmed_at 晚于 created_at（最大差 5 天）——确认动作会"重置年龄"，老素材永远不满 10 天。

### 4.2 设计（全修 + 保持10天）

1. **misfire 修复**（scheduler.py）：给三个 cron/interval 加 `misfire_grace_time`：
   - `hotspot_hook_library_cleanup`：`misfire_grace_time=3600`（迟到 1 小时内仍执行）；
   - `media_retention_cleanup`：`misfire_grace_time=3600`；
   - `check_scheduled_publish`（interval 1min）：`misfire_grace_time=120`（迟到 2 分钟内补跑，避免漏发）。
2. **启动补跑**（app.py lifespan / scheduler.start_scheduler）：启动后创建一次 catch-up 任务调用 `scheduler.cleanup_hotspot_hook_library()`（best-effort，try/except 包裹），让积压素材在下一次重启即被清理，不等 3:45。
3. **admin 手动端点**：`POST /api/admin/hotspot-hook-library/cleanup`（body: `{dry_run: bool}`），返回 `media_retention.cleanup_hotspot_hook_library` 的 report。权限 `require_role(UserRole.ADMIN)`。
4. **年龄基准改 created_at**（database.py:3376）：`datetime(created_at) < datetime('now', ?)`。created_at 是入库时间，"入库10天"语义正确，确认动作不再重置年龄。

### 4.3 执行范围

- `scheduler.py`：三个 add_job 加 misfire_grace_time。
- `app.py` 或 `scheduler.py`：启动 catch-up。
- `app.py`（或 routes）：admin 端点。
- `database.py:3376`：SQL 改 created_at。
- `media_retention.py`：无需改（wrapper 与函数本身已正确）。

### 4.4 测试

- `tests/test_media_retention.py`：现有测试补 created_at 基准用例（构造 confirmed_at 晚但 created_at 早的素材，断言按 created_at 判定候选）。
- 新增 admin 端点测试（dry_run 返回 report；非 admin 403）。
- 手工验收：重启后日志出现"热点 Hook 库滚动清理：删除>=1"；`/api/queue` 无异常。
