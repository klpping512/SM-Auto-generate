## 一、设计结论

### 1. chat 前置补丁的成功定义

真实模型成功必须同时满足：

- 浏览器调用 `/api/ai/chat` 成功返回。
- 返回对象中对应输出的 `source` 精确等于 `model`。
- 不出现 `source: safe_fallback`、`quality_warnings` 中的「AI 服务暂不可用」或无服务承诺模板。
- `model_role_configs.chat_text.request_options` 含 `enable_thinking:false`，且代码默认路由也保留同款兜底。
- 日志能区分正常模型返回、空内容重试和网络重试；不能只出现空白的 `error=`。

### 2. 热点视频回归的成功定义

至少跑一条真实热点视频链路，必须闭环到可播放文件：

- 热点 Hook 为已确认、可渲染、时长不少于 3 秒的素材。
- `planner_text`、`critic`、`video_evaluator` 均未因前置补丁回归为空回复或安全降级。
- 任务最终状态为成功，存在输出 MP4；媒体可被 `ffprobe` 读取，有视频轨，时长在目标范围内。
- `quality_report.provenance` / `coverage` 与实际链路一致，不得只凭 UI 文案判断。
- 日志无新的 `NameError`、模型空内容未处理、素材引用不存在或 FFmpeg 失败。

### 3. 批21测试专项的四个硬断言

| 专项 | 必须锁住的行为 |
|---|---|
| chain_mode 三链路 | `mix3` 至少 1 段 `za_stock_license`；`hotspot_owned` 保持热点 + 自有的默认行为；`owned_only` 无热点且不混入 za_stock |
| owned_only 分镜数 | 60 秒纯自有计划稳定给 8 段；模型超发时 `_planner_json` 截断，不足时仍拒绝；repair 提示条数跟随计划 |
| import_project 标签 | 话题词 + 前两个物流节点 + 链路标签 + 固定组合，去重后最多 8 个；链路条件不能串标签 |
| 审核即发布 | approve 后状态为 `queued`，若原来没有 `scheduled_at` 必须补当前时间；scheduler 能取到该项 |

## 三、前置补丁浏览器/API实测

### A. 重启和启动证据

按宿主已有启动方式重启服务，不新增端口、不改变代理配置。记录旧 PID、新 PID、启动时间和启动日志。若执行器无法操作宿主服务，明确标记“宿主声明”，不得写成通过。

启动后先确认首页或既有登录页能返回 200，再进入浏览器实测；项目没有可假设存在的 `/api/health` 路由。

### B. chat 真实模型验证

在浏览器登录后进入 Chat，选择抖音，输入一条具体但不依赖未提供事实的请求，例如：

> 生成一条 50–65 秒的南非物流短视频文案，主题是德班港拥堵时卖家应先核对哪些物流节点。

必须保存以下证据：

1. 浏览器 Network 中 `/api/ai/chat` 的请求和响应；响应中对应 output 的 `source:"model"`。
2. 页面展示的是模型生成内容，不是「AI 服务暂不可用」或无服务承诺的降级提示。
3. `logs/app.log` 中本次请求的时间窗口；若发生重试，记录 `模型调用重试`、`模型调用空内容重试` 或 `模型调用网络重试` 的完整行。
4. 本次请求没有新的 `error=` 空白异常；如失败，贴出异常 repr、HTTP 状态码和最终响应，不要只贴截图。

验收规则：

- `source:"model"` 是硬条件，`model_sanitized` 只能证明模型返回后经过安全整理，不能替代本条件。
- 有一次成功模型返回即可结束重试验证；不要为了“制造失败”修改线上代理或配置。
- 若输出仍是 `safe_fallback`，按顺序核查：DB request_options → 实际 route → 请求体 thinking 参数 → `call_text` 返回 payload → `_safe_chat_fallback` 日志。

### C. 热点视频回归

使用已有确认且可渲染的热点 Hook，走当前视频工作台的正式链路。至少完成一单 `hotspot_owned`；如宿主时间和素材允许，再补一单 `mix3`，以验证 za_stock 仍能进入计划。

记录：

- 项目 ID、任务 ID、所选 `chain_mode`、热点 Hook ID。
- 每个阶段的最终状态：Hook 锁定、脚本、项目构建、质量检查、渲染。
- `/api/video-generation/jobs/{id}` 最终 JSON 中的 `status`、`output_url`、`quality_report.provenance`、`coverage`。
- 实际输出路径和媒体检查结果：

```bash
ffprobe -v error -show_entries format=duration:stream=codec_type -of json /绝对路径/输出.mp4
```

必须核对：

- 至少 1 个热点视频场景；`hotspot_owned` 按库存条件出现自有场景；`mix3` 出现至少 1 个 `asset_source=za_stock_license` 且对应 `stock_required` 标记。
- 规划模型和质检模型均有可见文本结果；没有因 `call_text` 空内容重试耗尽导致 502/failed。
- MP4 有视频轨、时长合理、可播放；失败时保留任务 JSON、最近 100 行日志和失败阶段。

## 四、批21测试覆盖专项：执行设计

建议新增一个专用文件：`tests/test_batch21_coverage.py`。若执行器选择拆成多个文件，必须保持同样的四个分组和命名语义，不得把测试散落到无关文件。

所有测试必须使用 `tmp_db`，不能写真实 `data/logiflow.db`；模型调用使用 monkeypatch / MockTransport，不能消耗线上预算。

### A. chain_mode 三链路

测试目标函数：`hotspot_video_planner.plan_followup_scenes`，必要时补 API 层断言。

最小 fixture：

- 1–2 个 `review_status=confirmed`、`clip_status=ready`、每段至少 7 秒的热点事件。
- 至少 8 段 `asset_source=upload` 的 Buffalo 自有视频，动作/类别可区分。
- 至少 2 段 `asset_source=za_stock_license` 的授权素材。

必须覆盖：

1. `mix3`：热点场景不少于 1；自有场景存在；授权素材场景不少于 1，且 `stock_required is True`；总授权段不超过 2。
2. `hotspot_owned`：默认行为不被改写；有充足 Buffalo 覆盖时不强制塞 za_stock；有功能缺口或自有库存不足时，允许按既有规则补 za_stock。
3. `owned_only`：热点场景数为 0；授权素材场景数为 0；所有视频场景均为 Buffalo 自有；`chain_mode` 只在上层 snapshot/provenance 中表达，不要伪造热点。
4. provenance/coverage：若走 API/任务 handler，断言 `hotspot_video`、`owned_video`、`za_stock`、`chain_mode` 与实际场景来源一致，不能只断言字段存在。

### B. owned_only 分镜数和超发截断

测试目标函数：`hotspot_video_planner.plan_followup_scenes`、`app._planner_json`。

必须覆盖：

1. 60 秒 `owned_only` 在至少 8 个可用、动作不重复的自有片段下返回 8 个真实视频场景，不应返回 7 个。
2. `_planner_json(content, expected_scenes=8, ...)` 收到 9 段模型输出时只保留前 8 段。
3. 收到少于 8 段时仍抛出原有 `ValueError`，不能用截断逻辑掩盖库存/模型不足。
4. 每一段保留旁白和必要的 `text_overlay`；截断不能改变顺序、不能凭空补素材。
5. 若测试触及 repair prompt，断言 prompt 明确包含当前计划条数，而不是硬编码 7 或 8。

### C. `import_project` 标签 D3

测试目标函数：`static/editor.html` 中的 `buildImportHashtags`。沿用项目现有 Node 方式执行，不用浏览器 DOM。

fixture 需要覆盖：

- 标题含 `｜`，主题前有多个中英文片段。
- `brief.logistics_nodes` 至少 3 个，验证只取前 2 个。
- `chain_mode` 分别为 `mix3`、`hotspot_owned`、`owned_only`，并测试 `source_snapshot` 为对象和 JSON 字符串两种形态。

断言：

1. 主题词取标题 `｜` 前的前两个合法片段。
2. 物流节点只取前两个。
3. `mix3` 有 `南非素材` 和 `热点追踪`；`hotspot_owned` 只有 `热点追踪`；`owned_only` 两者都没有。
4. 固定组合包含 `南非物流`、`跨境电商`、`卖家出海`。
5. 重复标签只保留一次，最终长度始终 `<= 8`；输入缺失或非法时函数不抛异常。

### D. 审核即发布

测试目标：`POST /api/review/{item_id}` 的 approve 分支和 `database.get_scheduled_items`。

至少写两条 API/DB 测试：

1. 新建 `pending_review` 队列项，`scheduled_at=NULL`，以 reviewer/admin 调 approve；断言响应 200、状态变为 `queued`、`scheduled_at` 非空且可被 `get_scheduled_items()` 取出。
2. 新建已有 `scheduled_at` 的 `pending_review` 队列项，approve 后保持原时间，不被覆盖；状态仍为 `queued`。

同时断言：

- 审核门禁通过后才入队；`reject` 不得变成 `queued`。
- 时间格式与 scheduler 查询可比较，不能写 ISO `T` 格式或不可解析值。
- 使用真实 `tmp_db` 和最小合法用户/队列 fixture，不触碰生产库。
