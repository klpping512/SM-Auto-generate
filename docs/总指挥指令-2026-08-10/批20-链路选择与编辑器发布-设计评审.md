## 〇、背景

总指挥新做话题「出海南非，仓库里这步你核对了吗？｜50秒动态视频」，跑完后出现两个运行问题：

1. **没用确定好的视频生成链路**（热点素材+zastock+原有素材）——成片 8 个镜头**全部是原有素材库**，热点也没体现。
2. **视频生产完没有推入发布队列的按钮**——旧链路是：生产完自动进内容编辑器 → 自动写文案选 tag → 确认后推发布队列发布。

用户拍板方向：问题1 = **加显式链路选择**；问题2 = **恢复编辑器旧链路**。

## 一、根因（DB + 代码实证）

### 问题1：链路选择不存在，热点"素材"是常青剪自自有母片

DB 实证（项目 `a93aa2ba…` / job `bfa902fb…`）：

- `source_snapshot` 覆盖 = `{hotspot_video:1, owned_video:7, image:0, duration_ms:50673}`——名义上"热点1+自有7"，但：
- 唯一"热点"镜头（scene 1）的 `clip_ref` = `event_clip 274`，`library_origin='hotspot_event'`，`clip_path='assets/library/video/5a3ca714….mov'`，实为**常青通用镜头** `generic-warehouse-4`，**剪自 Buffalo 自有素材 asset 4「海外仓全景」（source='directory'）**——即"热点"在视觉上就是自有仓库画面。
- 8 个资产全部 Buffalo 自有（asset 4=directory，51/61/63=upload，123/124/133/140=local_directory），**0 个 `za_stock_license`**。
- 库里 `za_stock_license` 资产有 **61 个**，但从未被选中——因为 `asset_matching` 阶段 owned 素材匹配就够用，za_stock 永远是候补。

代码实证：

- **无任何显式链路选择机制**。分镜计划由 `_generate_topic_brief_video`（app.py:2353）内 `hotspot_video_planner.plan_followup_scenes(brief, related_events, owned_segments, ...)` 隐式决定——传入什么源就出什么源，没有"za_stock 场景"这一概念，也没有 `stock_required` 这样的场景标记。
- `asset_matching`（video_generation.py:744）的候选过滤只排除 `asset_hotspot_id` 非空项（:764），**不过滤 source**，所以 za_stock 片段理论上是候选，但排序/打分时自有素材常占优。

**结论**：不是"热点没匹配上"，是**链路组成根本没有显式表达**。要"三源必混"，必须在场景规划阶段就强制安排 za_stock 镜头，并在素材匹配阶段对该镜头限定 za_stock 资产。

### 问题2：publish 门禁永不通过 + 编辑器链路是死代码

代码实证（两处叠加导致"没按钮"）：

1. **`publish_allowed` 对普通视频永远不为 true**：
   - `quality_decision()`（video_generation.py:248-262）计算 `publish_allowed = tier=="publish" and score>=threshold`，但全文件**只在 internal_preview 分支 :957 被调用**，且该分支 :1202-1210 还显式写 `publish_allowed: False`。
   - 全库 grep `publish_allowed.*True` = **0 命中**。
   - 结果：video-project.html:579 的门禁 `job?.quality_report?.publication?.publish_allowed === true` **永不成立** → 渲染完成的视频没有任何"发布"入口。

2. **编辑器链路存在但从未被启用**：
   - `loadVideoProjectDraft(projectId)`（editor.html:718）已实现：能拉 `/api/video-projects/{id}`、挂视频附件、设 `preview_only`（succeeded 视频该值为 false，**发布不设防**）——但**全文件从未被调用**（死代码）。
   - editor.html:380-384：`?project_id=` 存在时直接重定向回 video-project.html，从不进入编辑器加载草稿。
   - 缺的只有：文案 body 没从脚本旁白拼出来、hashtags 是空数组。

发布队列链路本体是通的（editor `submitToQueue` → `pending_review` → queue.html 审核 → `/api/review/{id}` approve → `queued` → scheduler 每分钟扫 → 发布），**但发现一个断点**：

- `/api/review/{id}` approve（app.py:731-755）只调 `update_queue_status(item_id,"queued")`，**不设 `scheduled_at`**；
- scheduler 的 `get_scheduled_items()`（database.py:1667）硬性要求 `status='queued' AND scheduled_at IS NOT NULL AND scheduled_at <= now`；
- → **审核通过后若不在 queue.html 手动定时，就永远不发布**。这违背"确认无误后推到发布队列就发布"的预期。

## 二、方案A：显式链路选择 `chain_mode`

### 语义

| chain_mode | 含义 | 场景规划要求 |
|---|---|---|
| `mix3` | 热点 + za_stock + 自有（总指挥确定的三源链路） | ≥1 热点 Hook 开场 + **≥1 za_stock 场景（标 `stock_required:true`）** + 其余自有 |
| `hotspot_owned` | 热点 + 自有（**现状默认**） | ≥1 热点 Hook，其余自有；za_stock 仅作候补（现状） |
| `owned_only` | 纯自有 | 不依赖热点 Hook（需放宽热点硬门禁，见决策点 D1） |

### 落点（5 层）

1. **models.py**：
   - `TopicBriefCreateRequest`（:290）加 `chain_mode: str = Field(default="hotspot_owned", pattern=r"^(mix3|hotspot_owned|owned_only)$")`——紧挨 `freshness_mode`，完全照抄先例。
   - `TopicBriefGenerateRequest`（:315）加 `chain_mode: str | None = None`（None = 继承 brief 已存值）。
   - `TopicAutoPilotRequest`（:328）加 `chain_mode`，autopilot 创建 brief 时透传。
   - `TopicBriefUpdateRequest` 自动继承（它 extends Create）。

2. **DB**：`topic_briefs` 表加列 `chain_mode TEXT`（镜像 `freshness_mode TEXT`，`:297` 先例）。建表/迁移与 freshness_mode 同位置处理；旧行默认 `'hotspot_owned'`。

3. **app.py**：
   - `create/update topic brief` 端点：`chain_mode` 落库。
   - `autopilot_topic_brief_video`（:2320）：透传 chain_mode → brief 创建 → generate。
   - `scripting` handler（:2794）：构造 `TopicBriefGenerateRequest` 时把 brief 的 chain_mode 带上。
   - `_generate_topic_brief_video`（:2353）：读 chain_mode → 写入 `planning_brief`、传入 `plan_followup_scenes`、并**写入 `source_snapshot`**（`source_snapshot["chain_mode"]=...`）。

4. **hotspot_video_planner.plan_followup_scenes**：
   - 新增参数 `chain_mode`（默认 `hotspot_owned`）。
   - `mix3` 时：除热点 Hook 外，**强制分配 ≥1 个 `evidence_type="za_stock"`、`stock_required:true` 的场景**（时长由库存可用时长折算），其余自有。
   - `owned_only` 时：全自有场景，不锁热点 Hook（配合决策点 D1）。
   - 不足时抛覆盖类异常（复用现有 `ValueError` → 409 覆盖门禁文案，提示"za_stock 库存不足，请补南非素材或改链路"）。

5. **video_generation.py `asset_matching`（:744）**：
   - 对 `scene.get("stock_required")` 为真的场景：候选优先从 `source='za_stock_license'` 资产选段（在现有候选过滤 :764 处加 source 偏好/过滤）。
   - 无可用 za_stock 段 → 回退自有 + 记 `match_scenes` 警告 + `source_usage` 里暴露实际来源，让覆盖门禁/人工可见"链路未兑现"。

6. **video_composition_policy.py**：`source_usage_report` 增加 `za_stock` 计数（现只有 hotspot_video/owned_video/image），供 source_snapshot 与前端如实显示三源构成。

7. **前端**：brief 创建弹窗 + autopilot 面板加"视频生成链路"下拉（mix3/hotspot_owned/owned_only），存到 brief 后在 video-project 页展示 `source_snapshot.chain_mode` 与三源比例。

### 效果（对照本次失败视频）

选 `mix3` 后：场景规划必出 ≥1 南非素材镜头（source='za_stock_license'），热点 Hook 保持真实优先、常青兜底；成片 source_snapshot 呈现 `{hotspot_video:N, za_stock:≥1, owned_video:N}`，视觉上不再"全是原有素材"。

## 三、方案B：恢复编辑器旧链路（生产完 → 内容编辑器 → 确认 → 发布队列）

### 链路目标态

```
video-project 成功态 ──▶ 内容编辑器(editor.html?import_project=<id>)
   视频已自动挂载 + 文案已按脚本旁白自动写好 + 标签已自动选好
   ── 人工确认 ──▶ submitToQueue → pending_review
   ── queue.html 审核通过(approve) ──▶ queued(+scheduled_at=now)
   ── scheduler 自动发布 ──▶ published
```

### 改动（5 处，全部有实证）

**B-1（前端）video-project.html:579 门禁改掉 + 加"去内容编辑器"按钮**
- 现状：`if (status === 'succeeded' && job?.output_url && publication?.publish_allowed === true)` —— `publication` 恒 undefined，永不复用。
- 改为：`if (status === 'succeeded' && job?.output_url)` 即显示发布入口卡片，含两个按钮：
  - **「去内容编辑器」**：`location.href='/editor.html?import_project=' + encodeURIComponent(projectId)`（走旧链路：自动文案+选tag→确认→入队）。
  - 「加入发布队列」P3 直入按钮（批19 已实现，见决策点 D2 是否保留）。

**B-2（前端）editor.html:380-384 init 分支**
- 新增参数读取：`import_project`。
- 逻辑：`?import_project=` 存在时**不重定向**，改为调用 `loadVideoProjectDraft(importProjectId)`；`?project_id=` 分支保持不变（仍回 video-project 详情）。

**B-3（前端）editor.html `loadVideoProjectDraft` 补文案与标签**
- 现状已做：拉 `/api/video-projects/{id}` → 挂视频附件（`rendered_video`）→ 设 preview_only（succeeded=false，**发布不设防**）→ 切到 douyin tab。
- 补齐两处：
  - `body`：由 `linkedJob.quality_report.script.scenes` 按序拼接 `voiceover`（实证字段：scene[i].voiceover 逐段旁白），标题用 `script.title` 或项目标题。
  - `hashtags`：按"话题+物流节点+链路"派生（具体规则见决策点 D3）。
- 拼接后调用现有 `loadPlatformToEditor('douyin')` 即完成"自动写好文案+选好 tag"。

**B-4（后端）`/api/review/{id}` approve 后兜底 scheduled_at**
- 现状：approve 只 `update_queue_status(item_id,"queued")`，scheduled_at 恒 NULL → scheduler 永不取。
- 改为：approve 分支先取 item，若 `scheduled_at` 为空则 `update_queue_status(item_id,"queued", scheduled_at=now)`——**审核通过即发布**，符合旧链路预期（有定时则尊重原定时）。

**B-5（校验）发布队列全链路实证**
- editor submitToQueue（:1189）→ `POST /api/queue`（app.py:517，editor 草稿自动转 pending_review）→ queue.html 审核 → `/api/review/{id}` approve → queued → scheduler。B-4 补齐后链路闭环。

## 四、待总指挥拍板（4 个决策点）

- **D1｜`owned_only` 是否本轮做**：需要放宽热点硬门禁（`_generate_topic_brief_video` 的 `hotspot_count<1→409`），改动面更大。建议本轮只做 `mix3` + `hotspot_owned`，`owned_only` 下轮再说。
- **D2｜P3 直入按钮是否保留**：批19 已实现的「加入发布队列」（跳过审核直接 queued）与编辑器审核链路并存。建议**保留**（直发省事），但默认入口放"去内容编辑器"。
- **D3｜标签自动生成规则**：建议 = 话题核心词（从标题/主体词提取）+ 物流节点（brief.logistics_nodes）+ 链路标签（mix3 加 #南非素材 / hotspot 加 #热点追踪）+ 固定组合（#南非物流 #跨境电商 #卖家出海），上限 8 个。总指挥可改。
- **D4｜chain_mode 默认值**：建议默认 `hotspot_owned`（保持现行为，显式选 mix3 才混三源），避免无感改变既有出片。若希望"确定好的链路"成为默认，则默认 `mix3`。
